# 资源准入与防滥用

本项修复上架审查第 3 项：匿名安装身份可以反复创建，因此不能只按安装 ID 限流。安装身份继续用于数据隔离；来源网络和全局预算用于限制可消耗资源。实现不修改视频历史、安装令牌或 LLM 配置。

## 默认额度

所有 daily 配置均为**滚动 24 小时**，不是每天零点重置。更改 `api/.env` 对应变量后，应同步重启 API、Worker 和 scheduler。默认值和变量名完整列于 `api/.env.example`。

| 项目 | 单安装实例 | 同一来源 IP | 服务全局 |
| --- | --- | --- | --- |
| 新安装注册 | 不重复计数 | 20 次/24 小时 | 1000 次/24 小时 |
| 注册频率 | — | 10 次/分钟 | 100 次/分钟 |
| 写请求 | 20 次/分钟 | 60 次/分钟 | 600 次/分钟 |
| 读请求 | 120 次/分钟 | 360 次/分钟 | 3600 次/分钟 |
| 未结束分析任务 | 1 个 | 2 个 | 8 个 |
| 新受理分析及失败重试 | 20 次/24 小时 | 20 次/24 小时 | 200 次/24 小时 |
| ASR 预留时长 | 8 小时/24 小时 | 8 小时/24 小时 | 48 小时/24 小时 |
| 正在上传的会话 | 1 个 | 2 个 | 8 个 |
| 新受理上传声明字节 | 8 GiB/24 小时 | 8 GiB/24 小时 | 40 GiB/24 小时 |

单视频上限保持 4 小时；单媒体上限 4 GiB；单 X 任务临时预留 6 GiB；全局临时预留上限 20 GiB；磁盘需额外保留至少 1 GiB 空闲。排队、等待媒体和处理中都属于未结束分析任务，并非只计算正在占用 CPU 的任务。Worker 实际执行并发仍由 Celery 配置决定。

X 的浏览器上报时长不是可信 CPU 预算，因此**每个新受理的 X 分析/失败重试均按完整 4 小时计入 ASR 额度**，不按上报的几分钟扣费。默认同一 IP/安装实例每 24 小时最多受理 2 次 X ASR；全局最多 12 次。任务较短、失败或取消不会返还本轮预算。YouTube 读取已有字幕不消耗 ASR 额度。预算是资源保护计数，不是向用户收取费用。

## 一致性与失败行为

- PostgreSQL 的事务级 advisory lock 将注册、任务创建和上传创建的“检查额度—写入计数—创建资源”串行化。等待超过 2 秒返回 `admission_busy`，不绕过限制。测试用 SQLite 使用 `BEGIN IMMEDIATE`。
- 日额度写入 `quota_usage`，与资源创建在同一事务提交。重启进程、重启 Redis、重新安装插件、删除上传均不会返还这部分日额度；Redis 负责分钟限速，Redis 不可用时请求会被拒绝。
- 身份匹配的幂等注册不占新身份日额度。相同活动任务的恢复不算新任务；已完成缓存命中、历史/结果读取不扣日分析额度，但仍受请求频率限制。用户明确重新分析会创建新任务并扣额度。
- 已受理任务即使派发或执行失败，也计入日预算。失败任务再次主动重试也扣一次。失败/完成后释放未结束任务名额，历史保留。
- 全局临时预留 = 尚未清理的上传声明大小 + 未结束 X 任务数 × 单任务临时预留。完成、已消费和失败上传在实际清理前继续保留容量，过期清理/用户删除成功后释放。
- 磁盘检查使用媒体卷的可用空间，并要求能覆盖全部未释放预留、新预留与安全余量。已写入磁盘的字节不从预留中扣除，这是保守检查，可能提前拒绝任务。多机部署需共享同一个媒体存储卷或另行实现分节点容量管理。
- 全局临时预留是准入控制，不等于操作系统磁盘配额。仍需卷容量监控、失败清理告警和运行时文件限制；进程崩溃留下的文件由实际磁盘空间检查兜底，不能把逻辑预留当作磁盘实际占用统计。
- 配额账本不保存 API Key、字幕正文或原始 IP，只保存来源网络的 SHA-256 摘要、安装/资源 ID、用量和时间。IP 摘要是伪名化标识，并非不可逆匿名信息。scheduler 清理 48 小时以前且不支撑活动资源/存储预留的账本，不清理分析历史。

## 来源 IP 与代理

默认 `TRUSTED_PROXY_CIDRS=[]`，只读取 socket 对端地址，忽略用户提交的 `X-Forwarded-For`。IPv4-mapped IPv6 统一到 IPv4；IPv6 按 `/64` 聚合，避免轻易轮换隐私地址重置额度。同一公网出口/NAT 的用户会共享 IP 额度。

生产反向代理应配置**具体代理 IP/CIDR**，例如 `TRUSTED_PROXY_CIDRS=["10.20.0.5/32"]`，不要照抄示例 IP，更不要信任整个公网或所有内网。`/0` 配置会被拒绝。代理必须覆盖或正确追加真实 socket 来源地址到 `X-Forwarded-For`；服务从右向左去掉受信任代理，取第一个不受信任地址。受信任对端缺少合法链时拒绝请求，不回退到可伪造来源。

Compose 已加入 `uvicorn --no-proxy-headers`。其他启动方式也必须保留这个选项：应用自行解析受信任转发链，不能让 Uvicorn 预先改写 `request.client`。不要将 `--forwarded-allow-ips=*` 或其他通配信任作为替代。容器/代理/NAT 可能把全部来源显示为一个网关地址，此时会共享一份 IP 配额；上线前必须实际验证代理拓扑和来源解析。

IP 不是可靠的真人身份。多出口攻击仍可能绕过 IP 子额度，但所有来源共同受全局额度约束。更大规模公开服务还需网关防护、注册挑战/账户信誉及运维监控；这不是“完全杜绝滥用”的保证。

## 升级与验证

1. 暂停新任务受理；确认 Worker 没有活动/排队任务后再停服务。
2. 备份 PostgreSQL，保留现有 volume、环境文件、安装身份、加密密钥和扩展路径。
3. 执行 `alembic upgrade head`，迁移 `0010_resource_admission` 仅增加账本表/索引，不改历史或凭据。旧任务不补扣日额度；旧活动任务仍计入全局未结束数量。
4. 启动同版本 API、Worker、scheduler；验证健康检查和旧历史读取。
5. 重新构建扩展并在扩展管理页面重新加载，以显示新增的限额/容量错误提示。

回归覆盖多身份同 IP 限流、跨 IP 全局日额度、真实 PostgreSQL 并发准入、上传释放与日额度不退款、缓存不重复计费、伪造转发头、IPv6 地址归并、磁盘不足和账本清理。测试使用隔离数据库与模拟 provider，不消耗真实 LLM Key。
